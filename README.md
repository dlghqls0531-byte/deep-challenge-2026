# 아주 소중한 딥러닝 챌린지 2026 — 제출 코드

Qwen2.5-3B-Instruct 베이스 모델로 정수 정답 수학 문제를 푸는 추론 파이프라인입니다.
답안은 **모델 추론 결과만으로** 생성됩니다. 정답 조회(lookup) 로직, 외부 정답 데이터,
추론 시 네트워크 호출이 전혀 없습니다.

---

## 0. 제출 구성 요약 (검증 담당자용)

> **가중치 파일이 저장소에 없는 것이 정상입니다.**

| 항목 | 내용 |
|---|---|
| 모델 | `Qwen/Qwen2.5-3B-Instruct` **원본 그대로** |
| 파인튜닝 | **없음.** LoRA 어댑터, 추가 가중치 파일 일절 없음 |
| 가중치 병합 | 없음 |
| 성능 향상 요소 | **전적으로 추론 시점 기법** — 다중 라운드 생성 + 적응형 자기일관성 + 프롬프트 다양성 + 투표 |
| 필요 하드웨어 | NVIDIA GPU 1장 (VRAM 16GB, T4 기준). **CPU 실행 불가** |
| 2,000문제 소요 시간 | T4 1장 기준 **약 13시간** |

개발 기간 중 LoRA 파인튜닝(외부 데이터 SFT, 자기출력 RFT, DPO)과 학습된 검증기를
총 7회 시도했으나 **모두 베이스 모델보다 낮은 정확도**를 보여 최종 구성에서 제외했습니다.
측정 결과는 7절에 정리했습니다.

따라서 재현에 필요한 것은 **이 저장소의 코드 + HuggingFace 공개 베이스 모델** 둘뿐입니다.

## 2. 환경

제출 결과를 생성한 환경입니다.

```
Kaggle Notebook (GPU T4)
Python 3.12
torch 2.10.0+cu128
transformers 5.0.0
peft 0.19.1          # 어댑터 미사용 구성에서는 불필요
```

```bash
pip install -r requirements.txt
```

버전은 결과를 생성한 환경에 맞춰 고정했지만, 아래 조건만 만족하면 인접 버전에서도 동작합니다.

- `transformers` — `AutoModelForCausalLM.from_pretrained` 의 `dtype` / `torch_dtype`
  인자명 변경을 코드에서 둘 다 처리합니다 (4.x, 5.x 모두 가능)
- `peft` — **최종 구성에서는 사용하지 않습니다.** `--adapter-dir` 옵션을 쓸 때만 필요
- `torch` — CUDA 빌드 필요

**GPU 필수입니다.** `device_map={"": 0}` 로 단일 GPU에 적재하며, CPU 전용 환경에서는
실행되지 않습니다. VRAM 16GB(T4) 기준으로 검증했고, 모델 적재에 약 5.8GB,
생성 시 KV 캐시를 포함해 최대 약 12GB를 사용합니다.

`attn_implementation="sdpa"`, `float16` 고정입니다.
(T4에서 bfloat16 은 에뮬레이션되어 약 10배 느려 사용하지 않습니다. eager attention 은
fp16 + left padding 조합에서 출력이 붕괴하므로 sdpa 를 사용합니다.)

### 소요 시간

T4 1장, 기본 설정(`--k1 4 --k2 6`) 기준입니다.

| 문제 수 | 생성 횟수 | 예상 시간 |
|---|---|---|
| 100 | 약 700 | 약 40분 |
| 400 | 약 2,800 | 약 2.5시간 |
| 2,000 | 약 14,000 | 약 13시간 |

생성 1건당 약 3.2초입니다. `--k1`, `--k2` 를 줄이면 비례해서 짧아집니다.
동작 확인만 하실 경우 `head -n 51 test.csv > small.csv` 로 50문제만 돌리시면
약 20분에 끝납니다.

## 3. 실행 방법

### 3-1. 베이스 모델 내려받기 (1회, 온라인)

```bash
bash download_model.sh ./models/Qwen2.5-3B-Instruct
```

이후 추론 단계는 네트워크 없이 동작합니다.

### 3-2. 추론

`test.csv` 는 `id`, `question` 두 컬럼을 가진 CSV 입니다.

```bash
python src/run_inference.py \
    --test      test.csv \
    --model-dir ./models/Qwen2.5-3B-Instruct \
    --out       submission.csv \
    --work      ./work \
    --k1 4 --k2 6 \
    --seed 42
```

출력은 `id`, `answer` 두 컬럼의 `submission.csv` 입니다.

주요 인자:

| 인자 | 기본값 | 설명 |
|---|---|---|
| `--k1` | 4 | 1단계에서 전체 문제에 뽑는 샘플 수 (프롬프트 A) |
| `--k2` | 6 | 2단계에서 미결착 문제에 프롬프트별로 뽑는 샘플 수 |
| `--extra-prompts` | `B,C,C2` | 2단계에 사용할 프롬프트 |
| `--rounds` | `512 512 512` | 라운드별 `max_new_tokens` (누적 1536) |
| `--stage` | `all` | `1` 또는 `2` 만 실행 가능 (중간 제출용) |
| `--seed` | 42 | 샘플링 시드 |

## 4. 파이프라인

```
test.csv
   │
   ├─ 1단계   전체 문제 × k1 샘플 (프롬프트 A, T=0.8)
   │            → submission.csv 즉시 기록
   │
   ├─ 판정    한 문제의 파싱된 답이 모두 같으면 '결착'으로 보고 추가 생성 제외
   │            (적응형 self-consistency — 쉬운 문제에 예산을 쓰지 않음)
   │
   ├─ 2단계   미결착 문제 × k2 샘플 × {B, C, C2} 프롬프트
   │
   └─ 집계    프롬프트 동등 가중 투표
```

### 답 추출 (`src/mathx.py`)

생성 텍스트에서 다음 순서로 정수를 찾습니다.

1. `FINAL_ANSWER: <정수>` (프롬프트가 요구하는 형식)
2. `\boxed{...}`
3. `answer is ...` / `result: ...`
4. 마지막 3줄의 마지막 숫자

`10^15` 를 넘는 값은 파싱 오류로 간주해 버립니다.
분수·LaTeX 표기(`\frac{a}{b}`, `a/b`)는 나누어떨어질 때만 정수로 변환합니다.

### 절단 방지 (`src/genlib.py`)

`max_new_tokens` 를 512씩 최대 3라운드로 나눠 생성하고, 라운드마다
`FINAL_ANSWER` 로 끝났는지 검사해 끝난 시퀀스는 제외합니다.
길이 제한 때문에 풀이가 잘려 오답이 되는 문제를 막기 위한 구조입니다.

### 집계: 프롬프트 동등 가중 투표

프롬프트마다 후보 답의 득표율을 구한 뒤, 프롬프트 간에는 **동등 가중**으로 평균냅니다.

```
score(답) = (1/P) · Σ_prompt  [ 해당 프롬프트에서 그 답의 득표수 / 그 프롬프트 샘플 수 ]
```

샘플 수가 많은 프롬프트가 투표를 독점하지 않게 하기 위한 것입니다.
학습된 파라미터가 없어 과적합 여지가 없습니다.

## 5. 재현성

### 제출 답안을 만든 정확한 명령

최종 제출본(`submission.csv`)은 아래 명령으로 생성했습니다.

```bash
# 8/31 최종 실행에 사용한 명령 — 제출 후 확정값으로 갱신
python src/run_inference.py \
    --test      test.csv \
    --model-dir ./models/Qwen2.5-3B-Instruct \
    --out       submission.csv \
    --work      ./work \
    --k1 4 --k2 6 \
    --extra-prompts B,C,C2 \
    --rounds 512 512 512 \
    --temperature 0.8 --top-p 0.95 \
    --batch-size 64 --token-budget 45000 \
    --seed 42
```

`work/run_report.json` 에 실행 시점의 전체 인자와 통계가 기록됩니다.

### 결정성의 범위

생성은 `temperature=0.8`, `top_p=0.95` 샘플링을 사용합니다.
`--seed` 로 `torch.manual_seed` / `torch.cuda.manual_seed_all` 을 고정하며,
배치 구성도 입력에 대해 결정적입니다. 다만 GPU 커널의 비결정성 때문에
서로 다른 하드웨어에서 완전히 동일한 토큰열이 나온다고 보장하기는 어렵습니다.
집계 단계(투표)는 후보가 주어지면 완전히 결정적입니다.

중간 산출물은 `--work` 디렉터리에 남습니다.

```
work/candidates.csv    문제·프롬프트·샘플별 파싱 결과
work/run_report.json   실행 설정과 통계
```

`candidates.csv` 가 있으면 이미 끝난 (문제, 프롬프트) 조합은 건너뛰므로,
중단 후 같은 명령을 다시 실행하면 이어서 진행됩니다.
`submission.csv` 는 단계마다 다시 기록되어 언제 멈춰도 유효한 제출본이 남습니다.

## 7. 개발 과정에서 확인한 것

파이프라인 설계의 근거가 된 측정 결과입니다. (공개 리더보드 831문제 기준)

| 변경 | 점수 |
|---|---|
| 베이스 그리디 | 0.70156 |
| 자기일관성 k=4 | 0.73886 |
| k=8 | 0.76052 |
| k=16 | 0.77256 |
| + 프롬프트 다양성 (A·B·C·C2), 동등 가중 | 0.78339 |
| + 프롬프트별 샘플 12개로 심화 | **0.78580** |

- **생성 길이 부족이 초기 성능의 가장 큰 병목**이었습니다. `max_new_tokens` 384에서
  45%가 중간에 잘렸고, 1024~1536으로 늘리자 DEV 200 기준 0.52 → 0.66 으로 올랐습니다.
- 집계 방식(단순 다수결, 신뢰도 가중, 프롬프트 가중 지수 α 스윕 등)은 서로 바꿔도
  점수가 사실상 동일했습니다. 후보 집합이 점수를 결정하고 집계는 거의 영향이 없었습니다.
- 학습 쪽 시도(외부 풀이 SFT, 자기출력 RFT, 생성형 검증기)는 모두 베이스를 넘지
  못해 최종 구성에서 제외했습니다. 외부 풀이 SFT 는 모델의 풀이 길이를 468 → 337
  토큰으로 줄여 오히려 정확도를 떨어뜨렸습니다(DEV 0.6700 → 0.6200, p=0.009).
