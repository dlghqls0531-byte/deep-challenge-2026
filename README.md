# 아주 소중한 딥러닝 챌린지 2026 — 제출 코드

Qwen2.5-3B-Instruct 베이스 모델로 정수 정답 수학 문제를 푸는 추론 파이프라인입니다.
답안은 **모델 추론 결과만으로** 생성됩니다. 정답 조회(lookup) 로직, 외부 정답 데이터,
추론 시 네트워크 호출이 전혀 없습니다.

---

## 0. 제출 구성 요약 (검증 담당자용)

> **가중치 파일이 저장소에 없는 것이 정상입니다.**

| 항목 | 내용 |
|---|---|
| 모델 | `Qwen/Qwen2.5-3B-Instruct` **원본 그대로** |
| 파인튜닝 | **없음.** LoRA 어댑터, 추가 가중치 파일 일절 없음 |
| 가중치 병합 | 없음 |
| 성능 향상 요소 | **전적으로 추론 시점 기법** — 다중 라운드 생성 + 적응형 자기일관성 + 프롬프트 다양성 + 투표 |
| 필요 하드웨어 | NVIDIA GPU 1장 (VRAM 16GB, T4 기준). **CPU 실행 불가** |
| 2,000문제 소요 시간 | T4 1장 기준 **약 13시간** |

개발 기간 중 LoRA 파인튜닝(외부 데이터 SFT, 자기출력 RFT, DPO)과 학습된 검증기를
총 7회 시도했으나 **모두 베이스 모델보다 낮은 정확도**를 보여 최종 구성에서 제외했습니다.
측정 결과는 8절에 정리했습니다.

따라서 재현에 필요한 것은 **이 저장소의 코드 + HuggingFace 공개 베이스 모델** 둘뿐입니다.

제출 결과를 생성한 환경입니다.

```
Kaggle Notebook (GPU T4)
Python 3.12
torch 2.10.0+cu128
transformers 5.0.0
peft 0.19.1          # 어댑터 미사용 구성에서는 불필요
```

```bash
pip install -r requirements.txt
```

버전은 결과를 생성한 환경에 맞춰 고정했지만, 아래 조건만 만족하면 인접 버전에서도 동작합니다.

- `transformers` — `AutoModelForCausalLM.from_pretrained` 의 `dtype` / `torch_dtype`
  인자명 변경을 코드에서 둘 다 처리합니다 (4.x, 5.x 모두 가능)
- `peft` — **최종 구성에서는 사용하지 않습니다.** `--adapter-dir` 옵션을 쓸 때만 필요
- `torch` — CUDA 빌드 필요

**GPU 필수입니다.** `device_map={"": 0}` 로 단일 GPU에 적재하며, CPU 전용 환경에서는
실행되지 않습니다. VRAM 16GB(T4) 기준으로 검증했고, 모델 적재에 약 5.8GB,
생성 시 KV 캐시를 포함해 최대 약 12GB를 사용합니다.

`attn_implementation="sdpa"`, `float16` 고정입니다.
(T4에서 bfloat16 은 에뮬레이션되어 약 10배 느려 사용하지 않습니다. eager attention 은
fp16 + left padding 조합에서 출력이 붕괴하므로 sdpa 를 사용합니다.)

### 소요 시간

T4 1장, 기본 설정(`--k1 4 --k2 6`) 기준입니다.

| 문제 수 | 생성 횟수 | 예상 시간 |
|---|---|---|
| 100 | 약 700 | 약 40분 |
| 400 | 약 2,800 | 약 2.5시간 |
| 2,000 | 약 14,000 | 약 13시간 |

생성 1건당 약 3.2초입니다. `--k1`, `--k2` 를 줄이면 비례해서 짧아집니다.
동작 확인만 하실 경우 `head -n 51 test.csv > small.csv` 로 50문제만 돌리시면
약 20분에 끝납니다.

## 3. 실행 방법

### 3-1. 베이스 모델 내려받기 (1회, 온라인)

```bash
bash download_model.sh ./models/Qwen2.5-3B-Instruct
```

이후 추론 단계는 네트워크 없이 동작합니다.

### 3-2. 추론

`test.csv` 는 `id`, `question` 두 컬럼을 가진 CSV 입니다.

```bash
python src/run_inference.py \
    --test      test.csv \
    --model-dir ./models/Qwen2.5-3B-Instruct \
    --out       submission.csv \
    --work      ./work \
    --k1 4 --k2 6 \
    --seed 42
```

출력은 `id`, `answer` 두 컬럼의 `submission.csv` 입니다.

주요 인자:

| 인자 | 기본값 | 설명 |
|---|---|---|
| `--k1` | 4 | 1단계에서 전체 문제에 뽑는 샘플 수 (프롬프트 A) |
| `--k2` | 6 | 2단계에서 미결착 문제에 프롬프트별로 뽑는 샘플 수 |
| `--extra-prompts` | `B,C,C2` | 2단계에 사용할 프롬프트 |
| `--rounds` | `512 512 512` | 라운드별 `max_new_tokens` (누적 1536) |
| `--stage` | `all` | `1` 또는 `2` 만 실행 가능 (중간 제출용) |
| `--seed` | 42 | 샘플링 시드 |

## 4. 파이프라인

```
test.csv
   │
   ├─ 1단계   전체 문제 × k1 샘플 (프롬프트 A, T=0.8)
   │            → submission.csv 즉시 기록
   │
   ├─ 판정    한 문제의 파싱된 답이 모두 같으면 '결착'으로 보고 추가 생성 제외
   │            (적응형 self-consistency — 쉬운 문제에 예산을 쓰지 않음)
   │
   ├─ 2단계   미결착 문제 × k2 샘플 × {B, C, C2} 프롬프트
   │
   └─ 집계    프롬프트 동등 가중 투표
```

### 답 추출 (`src/mathx.py`)

생성 텍스트에서 다음 순서로 정수를 찾습니다.

1. `FINAL_ANSWER: <정수>` (프롬프트가 요구하는 형식)
2. `\boxed{...}`
3. `answer is ...` / `result: ...`
4. 마지막 3줄의 마지막 숫자

`10^15` 를 넘는 값은 파싱 오류로 간주해 버립니다.
분수·LaTeX 표기(`\frac{a}{b}`, `a/b`)는 나누어떨어질 때만 정수로 변환합니다.

### 절단 방지 (`src/genlib.py`)

`max_new_tokens` 를 512씩 최대 3라운드로 나눠 생성하고, 라운드마다
`FINAL_ANSWER` 로 끝났는지 검사해 끝난 시퀀스는 제외합니다.
길이 제한 때문에 풀이가 잘려 오답이 되는 문제를 막기 위한 구조입니다.

### 집계: 프롬프트 동등 가중 투표

프롬프트마다 후보 답의 득표율을 구한 뒤, 프롬프트 간에는 **동등 가중**으로 평균냅니다.

```
score(답) = (1/P) · Σ_prompt  [ 해당 프롬프트에서 그 답의 득표수 / 그 프롬프트 샘플 수 ]
```

샘플 수가 많은 프롬프트가 투표를 독점하지 않게 하기 위한 것입니다.
학습된 파라미터가 없어 과적합 여지가 없습니다.

## 5. 재현성

### 제출 답안을 만든 정확한 명령

최종 제출본(`submission.csv`)은 아래 명령으로 생성했습니다.

```bash
# 8/31 최종 실행에 사용한 명령 — 제출 후 확정값으로 갱신
python src/run_inference.py \
    --test      test.csv \
    --model-dir ./models/Qwen2.5-3B-Instruct \
    --out       submission.csv \
    --work      ./work \
    --k1 4 --k2 6 \
    --extra-prompts B,C,C2 \
    --rounds 512 512 512 \
    --temperature 0.8 --top-p 0.95 \
    --batch-size 64 --token-budget 45000 \
    --seed 42
```

`work/run_report.json` 에 실행 시점의 전체 인자와 통계가 기록됩니다.

### 결정성의 범위

생성은 `temperature=0.8`, `top_p=0.95` 샘플링을 사용합니다.
`--seed` 로 `torch.manual_seed` / `torch.cuda.manual_seed_all` 을 고정하며,
배치 구성도 입력에 대해 결정적입니다. 다만 GPU 커널의 비결정성 때문에
서로 다른 하드웨어에서 완전히 동일한 토큰열이 나온다고 보장하기는 어렵습니다.
집계 단계(투표)는 후보가 주어지면 완전히 결정적입니다.

중간 산출물은 `--work` 디렉터리에 남습니다.

```
work/candidates.csv    문제·프롬프트·샘플별 파싱 결과
work/run_report.json   실행 설정과 통계
```

`candidates.csv` 가 있으면 이미 끝난 (문제, 프롬프트) 조합은 건너뛰므로,
중단 후 같은 명령을 다시 실행하면 이어서 진행됩니다.
`submission.csv` 는 단계마다 다시 기록되어 언제 멈춰도 유효한 제출본이 남습니다.

## 6. 제출 답안 검증 절차

생성 단계는 온도 샘플링을 쓰므로 하드웨어가 다르면 토큰열이 달라집니다.
그래서 검증을 **결정적인 부분**과 **근사 재현 부분**으로 나눠 제공합니다.

### 6-1. 집계 재현 — 완전 결정적, GPU 불필요, 수 초

제출한 답안이 후보들의 파싱값만으로 만들어졌음을 확인합니다.

```bash
python src/aggregate_only.py \
    --candidates artifacts/candidates.csv \
    --test       artifacts/test_ids.csv \
    --out        /tmp/rebuilt.csv
diff /tmp/rebuilt.csv artifacts/submission.csv     # 출력 없음 = 일치
```

`artifacts/candidates.csv` 는 (문제, 프롬프트, 샘플) 단위로 **모델이 생성한 텍스트에서
추출한 정수 하나씩**을 담고 있습니다. 이 파일과 투표 코드만으로 제출본이 정확히
재현된다는 것은, 답안의 출처가 모델 생성물뿐이며 정답 조회가 개입하지 않았음을 뜻합니다.

### 6-2. 생성 재현 — 근사, GPU 필요

```bash
python src/run_inference.py --test artifacts/test_ids_with_questions.csv \
    --model-dir ./models/Qwen2.5-3B-Instruct --out /tmp/regen.csv \
    --work /tmp/regen_work --k1 4 --k2 4 --extra-prompts B,C,C2 --seed 42
```

같은 시드를 쓰지만 GPU 커널의 비결정성 때문에 개별 토큰까지 동일하지는 않습니다.
문제별 정답률과 후보 분포가 `artifacts/run_report.json` 의 통계와 유사하면
동일한 절차로 생성되었다고 볼 수 있습니다.

### 6-3. 2단계 실행 기록

최종 실행은 Kaggle 커밋의 12시간 제한 때문에 두 번에 나눠 수행했습니다.

```
1회차   --stage 1    전 문제 × k1 샘플 (프롬프트 A)
2회차   --stage 2    1회차에서 만장일치가 아니었던 문제만 × k2 샘플 × B/C/C2
```

`candidates.csv` 에 이어붙이는 구조라 한 번에 실행한 것과 결과가 같습니다.
`--stage all` 로 한 번에 돌려도 동일합니다.

## 8. 개발 과정에서 확인한 것

파이프라인 설계의 근거가 된 측정 결과입니다. (공개 리더보드 831문제 기준)

| 변경 | 점수 |
|---|---|
| 베이스 그리디 | 0.70156 |
| 자기일관성 k=4 | 0.73886 |
| k=8 | 0.76052 |
| k=16 | 0.77256 |
| + 프롬프트 다양성 (A·B·C·C2), 동등 가중 | 0.78339 |
| + 프롬프트별 샘플 12개로 심화 | **0.78580** |

### 8-1. 생성 길이가 초기 최대 병목이었습니다

`max_new_tokens` 384 에서 **생성의 45%가 문장 중간에 절단**되고 있었습니다
(정확히 384 에서 멈춘 샘플 603개). 512×3 라운드로 확대한 뒤:

```
DEV 200   0.52 → 0.66      McNemar p = 7.45e-09,  악화 0건
```

하이퍼파라미터 하나가 +14%p 였습니다.

### 8-2. 집계 방식은 점수에 영향이 없었습니다

8종을 비교했습니다 — 단순 다수결, 신뢰도 가중, 프롬프트 동등가중, 프롬프트별 정규화,
길이 z정규화, 가중지수 α = 0 / 0.25 / 0.5 / 0.75 / 1.

방식 쌍마다 **20~79문제에서 서로 다른 답**을 내지만 총점은 사실상 동일했고,
McNemar p 는 전 조합에서 0.25 를 넘었습니다.
후보 집합이 점수를 결정하고 집계는 거의 기여하지 않습니다.

### 8-3. 학습 시도 7회는 모두 베이스에 미달했습니다

모든 비교는 동일 셀에서 베이스와 나란히 측정했습니다 (DEV 500 그리디).

| 시도 | 결과 | 기전 |
|---|---|---|
| 외부 SFT 소규모 ×2 (약 2,000건) | −5.0%p | 문체 붕괴 (`n_line` 25.5→15.8, `boxed` 0.04→1.00) |
| 외부 SFT 대규모 ×1 (19,886건) | −5.0%p | 길이 붕괴 (468→337 토큰), 0.6700→0.6200, p=0.009 |
| 자기출력 RFT ×2 | ±0 | 시작 loss 0.21 — 학습 신호 없음 |
| 생성형 검증기 (GenRM) | 0 | 홀드아웃 AUC 0.9162 / +3.25%p (p=0.007), 리더보드 불일치 문제에선 순증 0 |
| DPO | −16.8%p | margin +75.7 폭발, 완결율 0.922→0.508, 0.6700→0.5020 |

외부 학습 데이터는 DEV·HELDOUT·리더보드·POOL 전량과 대조해 **35.0% 를 오염으로 제거**한
뒤 사용했습니다.

### 8-4. 남은 여지는 선택에 있습니다

```
후보 52개 중 정답 포함 (Oracle)   ≈ 0.94
실제 선택 정확도                   = 0.78580
capture                            ≈ 84%
```

이미 후보에 있는 정답의 약 16%를 골라내지 못합니다. 생성형 검증기가 이 지점을
겨냥했으나, 만장일치로 이미 해결되는 쉬운 문제에서만 이득이 나 전이되지 않았습니다.

### 8-5. 리허설 — 저장소 코드를 실전 조건에서 검증했습니다

2026-08-30, 개발 기간 중 한 번도 사용하지 않은 HELDOUT 400문제에 `src/run_inference.py`
를 그대로 실행했습니다.

```
종료 코드 0          소요 5.60h        후보 6,926개 → 2.91초 / 후보
제출본 400행         fallback 0건
정확도 0.7525 (301 / 400)              표준오차 ±2.2%p
k=8 만장일치 조기 종료  193 / 400 = 48.3%
```

만장일치 조기 종료율이 리더보드 831문제에서 49.7%, HELDOUT 400문제에서 48.3% 로
**1.4%p 차이 안에서 재현**되었습니다. 적응형 배분의 전제가 특정 문제 집합에
의존하지 않는다는 근거입니다.

한 번의 실행으로 큰 후보 풀(`k1=8`, `k2=6` × B·C·C2, 문제당 17.3개)을 만든 뒤,
그 풀을 부분추출해 **145종의 배분 정책을 오프라인으로 비교**했습니다.
정책마다 GPU 를 다시 쓰지 않으므로 5.6시간에 전수 비교가 끝납니다.

| 정책 | 정확도 | 맞힌 문제 | 문제당 후보 |
|---|---|---|---|
| `k1=4 k2=4` B+C+C2 | 0.7575 | 303 | 9.3 |
| **`k1=3 k2=3` B+C+C2 (채택)** | **0.7525** | **301** | **6.8** |
| `k1=6 k2=4` B+C | 0.7525 | 301 | 9.8 |
| `k1=6 k2=6` C+C2 | 0.7500 | 300 | 11.7 |

상위 10종이 300~303문제 구간에 있습니다. 최상위와 10위의 차이가 **3문제**로
표준오차 안이며, **8-2 의 결론이 처음 보는 문제에서 독립적으로 재현**되었습니다.
따라서 최고점이 아니라 예산 안정성을 기준으로 `k1=3 k2=3` 을 채택했습니다.

HELDOUT 0.7525 와 리더보드 0.78580 의 차이는 예산 차이입니다. 리더보드도 후보 8개
시점에서는 0.76052 였고, 같은 예산끼리 비교하면 0.8%p 차이로 오차 범위 안입니다.

### 8-6. 리허설에서 발견해 고친 것

프롬프트별 시드를 이름의 첫 글자에서 파생하면 `C` 와 `C2` 가 **같은 난수 스트림**을
받습니다. 프롬프트 다양성은 프롬프트들이 독립적으로 표집한다는 전제 위에 서 있으므로,
정렬된 레지스트리에서의 위치로 시드 블록을 나누는 `prompt_seed()` 를 도입했습니다
(`src/run_inference.py`). 1단계(프롬프트 A)의 시드는 그대로 두어 리허설 측정값과의
대응을 유지했습니다.
